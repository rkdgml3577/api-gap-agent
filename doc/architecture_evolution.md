# 구조 구체화 과정과 방향성

이 문서는 "업무 규칙 기반 API 검증 누락 탐지 Agent"의 구조를 **어떤 방향성으로, 어떤 순서로 구체화했는지** 기록한다. 단순 기능 목록이 아니라 각 결정의 *이유*에 초점을 둔다.

## 1. 문제 정의와 설계 원칙

**풀려는 문제:** 업무 규칙은 정의돼 있는데, 그 규칙을 검사하는 테스트가 빠진 곳(검증 누락)을 찾는다. 이때 **"테스트 누락"과 "구현 결함"은 별개**라는 점이 핵심이다. 테스트가 없다고 구현이 틀린 것은 아니며, 새 테스트가 통과한다고 기존 검증이 있었던 것도 아니다.

세 가지 설계 원칙을 축으로 삼았다.

1. **자율성** — 조사 순서를 코드가 지정하지 않는다. 모델이 상황을 보고 다음 도구를 스스로 고른다.
2. **증거 기반** — 모든 결론은 실제로 수집한 자료(규칙·스키마·테스트·실행 관찰)에 근거해야 한다. 추측으로 결론 내지 못하게 막는다.
3. **판정 분리** — "기존 검증 여부(coverage)"와 "구현의 규칙 준수 여부(implementation)"를 섞지 않는다.

이 원칙들이 이후 모든 구조 결정의 판단 기준이 됐다.

## 2. 뼈대 — 자율 판단 루프 (1단계)

가장 먼저 자율성을 구현했다.

- **LangGraph `decide ↔ execute` 루프** (`agent/graph.py`): 모델이 행동을 고르고(decide), 도구를 실행하고(execute), 결과를 보고 다시 판단한다. 고정 파이프라인이 아니다.
- **실제 MCP 연결** (`mcp_server.py`, `agent/mcp_client.py`): 규칙·스키마·테스트 조회, 후보 테스트 실행을 6개 도구로 제공. stdio로 분리된 실제 MCP 서버다.
- **로컬 sLLM** (`agent/llm.py`): Ollama `qwen3:8b`. 외부 API 미사용.
- **구조화 출력**: 행동을 JSON 스키마로 강제하고, 가능한 도구만 분기 스키마로 제시해 잘못된 호출을 원천 차단.

**방향성:** "모델이 자유롭게 고르되, 고를 수 있는 행동의 범위는 코드가 통제한다." 자율성과 안전성의 균형점.

## 3. 증거 가드레일 — 구조적 종료 검사 (2단계)

자율성만으로는 모델이 근거 없이 결론 낼 수 있다. 그래서 `validate_finish()`로 **종료 조건에 증거 요건**을 걸었다.

- 규칙을 읽고, 모든 기존 테스트를 열람하고, 스키마를 확인해야만 판정 가능
- `missing` 선언 전 후보 테스트를 실제 실행하도록 요구
- **판정 분리 구현**: `assess_coverage`로 기존 커버리지를 **먼저 확정**하고, 그 뒤 새 테스트를 실행. 새 테스트 통과가 원래 누락 판정을 바꾸지 못하게 잠금.

**방향성:** "구조적으로 증명 가능한 것만 결론으로 인정한다." 단, 이 검사는 인용의 *의미*나 진단의 *정확성*까지 보장하지 않는다는 한계를 처음부터 명시했다.

## 4. 실제 모델 실행에서 드러난 문제와 교정 (3단계)

실제 `qwen3:8b`로 돌리며 발견한 결함들을 순차 교정했다. 이 과정이 구조를 "작동하는" 수준으로 끌어올렸다.

| 문제 | 교정 | 이유 |
|---|---|---|
| 실행했는데도 `implementation`이 항상 `unknown` | 실행한 규칙은 unknown 금지, passed→conforms·assertion_failed→violates 강제 | "구현 결함 판정" 축이 실제로 작동하게 |
| 그 교정의 부작용으로 `incomplete`(결과 없음) | 거절 메시지를 규칙별로 구체화 + 프롬프트 명확화 | 작은 모델이 예산 안에 복구하도록 안내 |
| 후보 형식 반복 거절 (ORDER-003) | 정확한 JSON 형식을 프롬프트에 리터럴로 명시 | 모델이 검증 조건을 못 번역하던 문제 |
| 실행 1회 ~400초 | 낭비 스텝 제거 + 읽은 테스트 중복 전송 제거 + `num_predict` 축소 | 입력 처리가 시간의 60%였음 |

**방향성:** "거절은 벌이 아니라 안내다." 가드가 막을 때마다 *무엇을 어떻게 고치면 되는지*를 모델에게 돌려주는 피드백 루프로 설계했다.

## 5. 증거 가드레일 강화 — 인용 검증 (4단계)

구조 검사를 한 단계 더 조였다.

- **인용 grounding** (`_is_grounded`): 모든 finding의 근거는 실제 수집한 자료에 실재하는 토큰(파일 경로·테스트 함수명·실행 관찰)을 인용해야 한다. 날조·무근거 산문 차단.
- **전체 열람 통일**: covered/missing/uncertain 어떤 판정이든 모든 테스트를 읽은 뒤에만 가능.

과거 완료 결과 전체에 역검증해 **거짓 거절 0건**을 확인하고 적용했다.

**방향성:** "없는 근거를 지어내지 못하게." 단, 인용이 *실재하는가*(구조)는 막아도, 인용이 판정을 *의미적으로 뒷받침하는가*는 여전히 사람/판정기의 몫으로 남겼다.

## 6. 사람 승인 게이트 (HITL) — 교체 가능한 추상화 (5단계)

의미 검증의 공백을 메우기 위해 사람을 루프에 넣되, **나중에 LLM 판정기로 교체 가능**하도록 설계했다.

- `agent/approval.py`: `review(findings, context) → {approved, feedback, by}` 한 메서드로 고정된 인터페이스.
- `AutoApprover`(기본, 무중단) / `HumanApprover`(asyncio future로 일시정지, API로 재개).
- 그래프의 `finish` 직전에 삽입. 반려 시 피드백을 revision으로 모델에 돌려 재조사.
- `APPROVAL_MODE=auto|human`으로 선택. **미래에 `LLMApprover`를 추가하고 `|llm` 한 줄만 더하면** 그래프·서버·UI 변경 없이 교체된다.

**방향성:** "지금 필요한 것(사람)과 나중에 올 것(LLM)을 같은 자리에 꽂을 수 있게." 기술을 미리 넣지 않되, 들어올 자리는 비워 둔다.

## 7. 승인 기준 + 과잉결론 방지 (6단계)

승인 게이트가 "항상 멈춤"이면 비효율적이고, 모델이 억지 결론을 내는 것도 막아야 한다. **LLM 없이 규칙 기반**으로 해결했다.

- **승인 기준** (`review_reasons`): 고위험 판정(`violates` 또는 `uncertain`)일 때만 사람 승인을 요구. 그 외는 자동 통과. `APPROVAL_TRIGGERS`로 조정.
- **과잉결론 방지**: ① `covered`는 규칙 문서가 아니라 **실제 테스트**를 인용해야 인정 ② 근거 부족·규칙 충돌 시 confident한 판정 대신 `uncertain`/`unknown`으로 물러서도록 가드+프롬프트에 명시.

**방향성:** "사람은 위험한 결정에만 부른다. 모델은 모를 때 모른다고 말하게 한다."

## 8. 확장 평가셋 — RAG의 근거 마련 (7단계)

현재 코퍼스는 ~580토큰(3규칙·3테스트)으로 작아, 벡터 검색(RAG)을 쓸 이유가 없다. 억지로 RAG를 넣는 대신, **RAG가 의미를 갖는 조건을 먼저 만들었다.**

- `evaluation/expanded/`: 실제 ORDER 규칙(바늘)은 유지하고, 의미적으로 닮은 범위 밖 distractor 규칙 36개·테스트 12개(건초더미)를 추가. 코퍼스 ~5,000토큰(8배).
- `CORPUS=default|expanded` 스위치로 기존 데모와 격리.

**방향성:** "기술은 그것이 푸는 문제가 실재할 때 넣는다." 교수님 피드백("개선 근거 없는 기술 추가는 의미가 약하다")에 맞춰, RAG 도입 전에 "전부 주입 vs RAG" 비교 실험의 토대를 먼저 깔았다.

## 전체 구조 요약

```
사용자: 범위·평가환경 선택
      │
      ▼
[decide] 가능한 행동 계산 → 모델이 자율 선택
      │                          ▲
      ▼                          │ (관찰·거절 피드백)
[execute] MCP 도구 실행 ──────────┘
      │
      ├─ 규칙/스키마/테스트 조사 → assess_coverage (기존 커버리지 확정)
      ├─ 누락 후보 테스트 생성·실행
      └─ finish
           │
     [증거 가드] validate_finish: 전체열람·인용grounding·실행근거·판정분리
           │
     [승인 게이트] 고위험(violates/uncertain)만 사람 승인 ← 나중에 LLM 교체 가능
           │
      completed / incomplete
```

## 일관된 방향성 한 줄 요약

> **"모델에게 자율을 주되, 코드로 증거를 강제하고, 모를 때 물러서게 하며, 위험할 때만 사람을 부른다. 기술은 그 기술이 푸는 문제가 실재할 때만 넣는다."**

## 남은 방향 (다음 단계)

1. **단일 Agent 평가 강화** — F1·오탐률, 변이별 반복 실행 통계, 충돌·근거부족 시 과잉결론 방지의 정량 검증
2. **오류 원인 단계 분석** — 규칙 해석/후보 생성/실행 해석 중 어디서 틀리는지
3. **(조건부) 멀티 에이전트** — 위 분석이 특정 단계를 병목으로 지목할 때만, 동일 평가로 단일 vs 멀티 비교
4. **RAG** — 확장 평가셋 위에서 "전부 주입 vs 검색" 비교로 타당성 수치 증명
5. **LLM 판정기** — 승인 게이트 자리에 의미 검증 추가 (인용이 판정을 뒷받침하는지)

## 제품화 방향: 임의 API 온보딩

현재 구조는 고정된 주문 서비스를 대상으로 하는 **데모·평가 하버스**다. 다른 조직의 API를 받으려면 타깃이 코드에 박혀 있어 여러 곳을 수정해야 한다. 이 결합을 끊고 "API를 꽂는 입구"를 만드는 것이 제품화의 핵심이다.

### 지금 하드코딩된 결합점
- 타깃 API 자체: `sample_service/app.py` (테스트도 `create_app()`을 in-process로 import)
- 후보 검증 기대값: `tools/runner.py` (ORDER-001/002/003의 상태코드·경계값이 코드에 고정)
- 규칙↔오퍼레이션 매핑: `agent/graph.py`의 `RULE_OPERATIONS` (3개 고정)

### 타깃 API가 필요로 하는 입력 4가지
1. **API 명세** — OpenAPI 스펙 (이미 스키마를 OpenAPI 형식으로 읽으므로 외부 스펙 파일/URL로 교체만 하면 됨)
2. **호출 대상** — 테스트를 실제로 날릴 base URL(스테이징/샌드박스) + 인증 ← 지금 없는 "API를 받을 곳"
3. **업무 규칙** — 자연어 문서 (이미 파일 기반)
4. **기존 테스트** — 대상 조직의 테스트 디렉터리 경로

### 권장 모델: 블랙박스 + 타깃 매니페스트
조직 코드를 레포에 넣지 않고, 매니페스트 하나로 타깃을 주입한다.

```yaml
# target.yaml (업로드/작성)
name: acme-orders
openapi: ./specs/acme.json          # 또는 https://api.acme.com/openapi.json
base_url: https://staging.acme.com  # 테스트를 날릴 곳
auth: { header: Authorization, value_env: ACME_TOKEN }
rules: ./rules/acme_rules.md
existing_tests: ./tests/
```

화면에서는 "① 스펙 업로드 → ② 스테이징 URL·토큰 → ③ 규칙 문서 → ④ 기존 테스트 폴더"의 온보딩 마법사가 이 역할을 한다. 생성된 테스트는 in-process `TestClient`가 아니라 httpx로 `base_url`을 호출한다.

### 전제 조건 (가장 큰 벽)
`runner.py`의 하드코딩된 후보 검증을 **규칙 해석기**로 대체해야 한다. 지금은 규칙을 미리 알아 기대값을 코드에 박았지만, 임의 조직의 규칙에서는 불가능하다. 규칙 문서에서 기대값·경계·상태 전이를 구조화해 뽑아내는 단계(발전 단계 "규칙 자동 해석")가 선행되어야 블랙박스 온보딩이 성립한다. 이 지점에 LLM이 정당하게 필요하다.

### 단계적 경로
1. 타깃을 설정으로 외부화 (`sample_service`/스펙/URL/규칙/테스트 경로를 `target.yaml`로; 현재 데모는 기본 타깃)
2. 러너를 base_url 호출(httpx) 모드로 확장
3. 규칙 해석기 도입 — 하드코딩 검증 제거
4. 온보딩 UI (4단계 업로드 마법사)
