## 0. 오프닝 — 문제와 대상 (약 40초)

안녕하세요. 저는 **업무 규칙 기반 API 검증 누락 탐지 Agent**를 만들었습니다.

먼저 이게 **누구의 어떤 고통**을 푸는지부터 말씀드리겠습니다.
개발 현장에는 "주문 수량은 1에서 100 사이", "남의 주문은 조회 못 함" 같은 **업무 규칙**이 문서로 정해져 있습니다. 그런데 **그 규칙이 실제로 테스트되고 있는지**는 아무도 확신하지 못합니다. 수백 개 규칙과 테스트를 사람이 일일이 대조하는 건 사실상 불가능하거든요.

이 고통을 가장 크게 느끼는 사람은 **QA 엔지니어**이고, 특히 **규제 산업이나 레거시 코드베이스**에서는 "검증 안 된 규칙"이 곧 리스크가 됩니다.

제 Agent는 이걸 자동화합니다. 그러면 지금부터 README를 따라 보여드리겠습니다.

## 1. 진행 사항 소개 (약 1분)

[화면: README "1. 진행 사항 소개"]

**먼저 프로젝트 주제입니다.**
핵심은 두 가지를 **섞지 않고 구분**하는 겁니다.
하나는 **검증 누락** — 규칙을 검사하는 테스트가 아예 없는 것.
또 하나는 **구현 결함** — 프로그램이 규칙을 실제로 어기는 것.
이 둘은 다릅니다. 테스트가 없다고 프로그램이 틀린 건 아니고, 새 테스트가 통과한다고 기존 검증이 있었던 것도 아닙니다. 저는 이 분리를 **코드로 강제**했습니다.

주요 동작은, AI가 규칙·명세·기존 테스트를 **스스로 조사**하고, 규칙별로 기존 검증 여부를 확정한 뒤, 누락된 부분을 **직접 테스트로 만들어 실행**해서 결과를 보고하는 흐름입니다.

**다음으로, 이번에 추가·수정한 작업입니다.**
기존 뼈대 위에서 실제 모델을 돌려보며 결함을 찾아 고쳤는데요, 대표적으로 — 구현 판정 정확화, 증거 가드레일 강화, 사람 승인 게이트, 과잉결론 방지, 그리고 평가 체계와 RAG 비교까지 추가했습니다. 자세한 내용은 2장에서 말씀드리겠습니다.

## 2. 사용한 기술 요소 — 무엇을, 왜 (약 2분)

[화면: README "2.1 적용한 기술 요소"]

여기서 가장 강조하고 싶은 건, **각 기술을 "멋있어서"가 아니라 구체적 문제를 풀려고 썼다**는 점입니다.

- **LangGraph 자율 루프** — 조사 순서를 코드로 고정하면 규칙마다 다른 경로를 못 다룹니다. 그래서 AI가 관찰 결과를 보고 다음 행동을 스스로 고르게 했습니다.
- **로컬 AI(Ollama)** — 검사 대상인 규칙·코드가 민감할 수 있어 외부로 안 보내고 제 컴퓨터 안에서 돌립니다.
- **MCP** — 도구를 AI와 분리해서, 예를 들어 **평가 정답 파일은 못 보게** 접근을 통제했습니다.
- **구조화 출력** — 자유 텍스트는 파싱 실패나 오호출을 냅니다. JSON 스키마로 행동을 강제했습니다.
- **의존성 주입** — 지금은 사람이 승인하지만, 나중에 LLM 심판으로 **갈아끼울 수 있게** 설계했습니다. 인터페이스만 고정하면 그래프 수정 없이 교체됩니다.
- **RAG** — 자료가 많아지면 전부 주입이 부담이라 관련된 것만 검색하도록 했고, 효과를 수치로 측정했습니다.
- 그리고 **모듈화, 단위 테스트 22개, 증거 기반 가드레일**이 있습니다.

반대로 **멀티 에이전트와 LangSmith는 일부러 안 썼습니다.** 지도 피드백대로 단일 Agent의 정확도부터 안정화하는 게 순서라고 판단했기 때문입니다. "쓸 이유가 없으면 안 쓴다"는 것도 하나의 판단이라고 생각합니다.

[화면: README "2.3 기능별 화면 캡처" — analysis-flow.png]

실제 화면입니다. 왼쪽이 **진행 과정**인데, 파란 "판단"으로 다음 행동을 고르고 회색 "관찰"로 결과를 확인하는 과정이 단계별로 쌓입니다. 오른쪽이 **분석 결과**로, 규칙별로 검증 누락인지, 구현이 규칙을 지키는지를 분리해서 보여줍니다.

[화면: approval-gate.png]

이건 **사람 승인 게이트**입니다. ORDER-003이 **규칙 위반**으로 판정되자, 종료 직전에 멈추고 사람에게 승인을 요청한 화면입니다. 승인하면 완료, 반려하면 다시 조사합니다. 위험한 판정일 때만 사람을 부르도록 기준을 세웠습니다.

## 3. 느낀 점과 향후 (약 1분)

[화면: README "3. 느낀 점 및 향후 개선 사항"]

가장 교훈적이었던 건 **과잉결론 방지**였습니다.
처음에 "규칙이 충돌할 때 AI가 억지로 결론 내리지 않는가"를 측정했더니, **기권율이 0%** 였습니다. 무조건 단정하더라고요.
그래서 충돌을 감지해 "판단 보류"로 물러서게 만들었는데, 이번엔 다른 가드가 그 근거를 거절하는 **부작용**이 생겼습니다. 이걸 다시 수정해서 결국 **기권율을 100%까지** 올렸습니다.
"측정 → 시도 → 부작용 발견 → 수정"의 과정 자체가, 가드끼리 서로 간섭할 수 있다는 걸 배운 값진 경험이었습니다.

향후로는 **멀티 에이전트 비교 실험, LLM 의미 판정기, 규칙 자동 해석**, 그리고 다른 회사 API를 꽂을 수 있는 **임의 API 온보딩** 구조를 계획하고 있습니다.

## 4. Before / After — 수치로 증명 (약 1분)

[화면: README "4. Before / After 비교"]

마지막으로 개선을 숫자로 보여드리겠습니다.

- **구현 판정 정확화**: 기존엔 결함이 있어도 "미확인"만 나왔는데, 수정 후 버그 환경에서 **결함 탐지 F1이 1.0**, 정상 환경에서 누락 recall이 **0.5에서 1.0**으로 올랐습니다. 그리고 "검증 누락"과 "구현 결함"을 혼동하지 않는 **분리 정확도도 1.0**입니다.

- **과잉결론 방지**: 방금 말씀드린 대로 **기권율 0에서 1.0, 오탐률은 1.0에서 0**으로 개선됐습니다.

- **RAG 비교**: 이건 솔직하게 말씀드리면 **"항상 유리"가 아니라 "조건부 유리"**였습니다. 쉬운 경우엔 차이가 없었고, AI가 헤매던 어려운 경우에만 **완료율이 두 배, 시간·토큰이 15~18% 줄었습니다.** 정확도 자체는 못 올렸고요. 저는 이걸 과장하지 않고 "언제 효과가 있고 언제 없는지"를 수치로 보여드리는 게 더 정직하다고 생각했습니다.

## 마무리 (약 20초)

정리하면, 이 프로젝트는 **AI에게 자율을 주되 코드로 증거를 강제하고, 모를 때는 물러서게 하며, 위험할 때만 사람을 부르는** 구조입니다. 그리고 모든 기술은 **그 기술이 푸는 문제가 실재할 때만** 넣었습니다.

아직 실제 API가 3개뿐인 작은 평가셋이라는 한계가 있지만, 그 한계까지 솔직하게 측정하고 기록했습니다. 들어주셔서 감사합니다.

---

### 예상 질문 대비 (메모)

- **"왜 멀티에이전트 안 썼나요?"** → 단일 Agent 정확도를 먼저 수치로 확보하는 게 순서. 개선 근거 없이 기술만 추가하면 의미가 약해진다고 판단.
- **"RAG 효과가 작은데 왜 넣었나요?"** → 큰 코퍼스에서 예산 압박 완화 효과를 확인했고, "조건부 유리"임을 수치로 드러낸 것 자체가 결과. 실제 API가 늘면 효과도 커질 것으로 기대.
- **"정확도 100%인데 과적합 아닌가요?"** → 맞습니다. 고정된 소규모 평가셋이라 일반 정확도가 아니며, 실제 API 확장이 다음 과제라고 명시했습니다.
- **"기권 시 incomplete가 1/3인데?"** → 기권 경로가 더 어려워 예산을 초과하는 비용. 트레이드오프로 기록해뒀습니다.
